# FastAPI revamp recommendation

## Repository findings

The current `working-v1` branch is a small modular commerce application with a Spring Boot 4 / Java 17 backend, React 19 + Vite frontend, PostgreSQL, products, categories, carts, orders, and custom access/refresh-token authentication.

Primary repository evidence:

- [Backend dependencies](https://github.com/angelfila2/eccomerce-site/blob/working-v1/pom.xml)
- [Frontend dependencies](https://github.com/angelfila2/eccomerce-site/blob/working-v1/frontend/package.json)
- [Database configuration](https://github.com/angelfila2/eccomerce-site/blob/working-v1/src/main/resources/application.properties)
- [Checkout implementation](https://github.com/angelfila2/eccomerce-site/blob/working-v1/src/main/java/com/example/ecoomerce_site/orders/OrderService.java)
- [Frontend API/auth client](https://github.com/angelfila2/eccomerce-site/blob/working-v1/frontend/src/api/api.js)

The main risks to correct during the revamp are hard-coded local configuration, schema changes driven by `ddl-auto=update`, a custom JWT refresh flow, minimal automated testing, and checkout stock updates without an explicit database row-locking strategy.

## Recommended target stack

Build an API-first **modular monolith**, not microservices.

| Layer | Recommendation |
|---|---|
| Runtime | Python 3.13 |
| Web/API | FastAPI, Pydantic v2, Uvicorn |
| Database | PostgreSQL |
| ORM | SQLAlchemy 2.x with typed declarative models |
| Migrations | Alembic; never create or update production schemas at application startup |
| PostgreSQL driver | `psycopg` 3 initially; use synchronous SQLAlchemy request handlers unless measured concurrency requirements justify async |
| Authentication | Same-origin secure HttpOnly session cookies for the browser, or standards-based OAuth2/OIDC when external/mobile clients are required; avoid inventing another refresh-token protocol |
| Background work | Start with FastAPI lifespan/background hooks only for non-critical short work; use Celery + Redis for durable email, payment, webhook, and inventory jobs |
| Cache/rate limits | Redis, added only when there is a demonstrated need |
| Object storage | S3-compatible storage for product images; store object keys/metadata in PostgreSQL |
| API contract | OpenAPI generated by FastAPI; generate a TypeScript client for the frontend |
| Frontend | Keep React/Vite for the first migration; convert new and touched code to TypeScript and choose one component/styling system |
| Testing | pytest, pytest-asyncio only if async DB access is used, HTTPX/TestClient, factory_boy, and real PostgreSQL integration tests |
| Quality | Ruff for lint/format, mypy or Pyright for static checking, pre-commit, `uv` with committed `uv.lock` |
| Delivery | Docker multi-stage image, GitHub Actions, managed PostgreSQL, secrets from environment/secret manager, Sentry plus structured JSON logs |

FastAPI is a good fit because it is API-first, type-driven, provides dependency injection, and generates OpenAPI and interactive documentation from the application. These are documented FastAPI features: <https://fastapi.tiangolo.com/features/>.

SQLAlchemy supports both synchronous and asyncio ORM access. Async sessions are mutable transaction objects and must not be shared across concurrent tasks, so async should be treated as an engineering choice rather than a default: <https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html>.

Use `uv` for project/dependency management and commit its universal lockfile for reproducible environments: <https://docs.astral.sh/uv/guides/projects/>.

## Suggested module boundaries

```text
app/
  api/              # HTTP routers, request/response schemas
  core/             # configuration, security, logging, errors
  db/               # engine, sessions, Alembic integration
  accounts/
  catalog/
  inventory/
  carts/
  orders/
  payments/
  notifications/
  integrations/
tests/
```

Each business module should own its SQLAlchemy models, repository queries, service/use-case functions, schemas, and tests. Routers should be thin: validate input, call a use case, and translate the result to HTTP. Do not create a generic repository/service abstraction until repetition proves one is needed.

## Commerce-specific correctness rules

- Treat money as `Decimal`/PostgreSQL `NUMERIC`, never float. Store currency explicitly.
- Snapshot product name, SKU, unit price, tax, and discounts onto order items; historical orders must not change when the catalog changes.
- Make checkout one short database transaction. Lock inventory rows (`SELECT ... FOR UPDATE` or an atomic conditional update), validate stock, create the order, decrement stock, and commit.
- Give order creation and payment/webhook handling idempotency keys and unique database constraints.
- Use an outbox table when a committed order must reliably trigger external work.
- Model order and payment state transitions explicitly; do not expose arbitrary status updates.
- Put authorization in use cases as well as route dependencies. Admin identity is not sufficient evidence that every operation is allowed.

## Migration sequence

1. Freeze and document the existing HTTP contract with characterization tests against the Java backend.
2. Create the FastAPI skeleton, configuration, PostgreSQL connection, Alembic baseline, CI, linting, and health checks.
3. Migrate read-only catalog/category endpoints first and point the existing React client at them.
4. Migrate accounts/auth, preferably behind the same origin to simplify cookies and CSRF protection.
5. Migrate carts, then orders/checkout with concurrency and idempotency tests before switching traffic.
6. Add payments, webhooks, image storage, and durable background workers only after the core transaction model is solid.
7. Remove the Spring service after API parity, data reconciliation, and rollback testing.

## Decision summary

FastAPI is viable and a good choice for this project, provided the team accepts that it supplies the API framework rather than a complete commerce platform. The recommended baseline is **Python 3.13 + FastAPI + Pydantic 2 + SQLAlchemy 2 + Alembic + PostgreSQL**, retaining the React/Vite frontend during the backend migration. Keep it as one deployable modular monolith until scale or team ownership creates a concrete reason to split it.
